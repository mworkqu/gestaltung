# Studio CAD backend (P5-15d)

## For the owner (plain words)

- Today every Studio 3D model (the case, its lid, the printable holders) is built **inside the customer's browser**. Nothing is sent to a server, it costs nothing, and it works now. This does not change.
- This page records exactly what the Studio would send to a **future, more precise builder** (CadQuery on the same Google Cloud machine that already builds AI models) and what it would send back: a 3D-print file (STL) and an engineering file (STEP) per object. The point is that the customer sees the same product either way.
- The switch is one optional setting, `studio_cad`. It is **off and not wired**: even if you set it to `cadquery` today the Studio ignores it and keeps using the browser. Nothing to do now.
- When we build it: first only you (admin) would see it, with timeouts and a cost cap, like the existing `cad_engine = admin` rollout. Your Google budget alerts (USD 1 / 5 / 10) already cover this worker.

## Engineer section

### What exists

`lib/studio/cad-adapter.ts`: `CadBackend` (`buildEnclosure`, `buildMechPart`), `BrowserCadBackend` (three.js + three-bvh-csg; the only implementation), `CadQueryBackend` (stub that throws "not enabled"), `parseStudioCadSetting`, `getCadBackend(setting)`.
`lib/studio/cad-setting.ts`: `getStudioCadSetting()` reads `store_settings.studio_cad` (cookie-free anon client, `unstable_cache`, tag `store-settings`). Missing row, malformed value or read error gives `"browser"`; any other value gives `"browser"` plus a `console.warn`.

### Request: `POST /studio/build` (future)

Units mm, Z up, origin at the centre of the footprint. The server must accept this JSON unchanged:

| Field | Type / source | Notes |
|---|---|---|
| `schemaVersion` | `1` | bump only with schema.ts |
| `units` | `"mm"` | anything else: 422 |
| `libraryVersion` | string | lets the server resolve `partId`s itself; parts are also sent in full so the server needs no copy of the library |
| `enclosure` | `EnclosureSpec` (schema.ts) | template, proportions, cornerRadius, edgeFillet, wall, clearance, lid, vents, feet, finish, colour, label |
| `layout` | `LayoutResult` (layout.ts) | `layout[]` {instanceId, pos, rotZ}, `bbox`, `footprint`, `height`, `bodyHeight`, `pokeHeight` |
| `parts[]` | per instance: `instanceId`, `partId`, `dims`, `mount`, `ports` | from `LibraryPart` |
| `mech` | `MechPart[]` | id, template, params, forInstance, printable |
| `plan` | output of `planEnclosure()` | `dims` (W, D, H, splitZ, innerW/D/H, floorZ, contentOffset, shape), `placed` (layout after `settleLayout`, e.g. the PIR lifted through the lid), `cutouts[]`, `keyholes[]` (wall_plate), `label` (raised text plan or null; `labelSkipped` says why), `vents[]` |

`plan` is the key decision: the placement of ports, the PIR poke-through lift and the vent grid are computed by TypeScript (`enclosure/templates.ts`, `enclosure/cutouts.ts`). The server **does not recompute them**; it cuts what `plan` says. That keeps one source of truth and makes the two backends agree by construction. A cut-out is a prism: `center`, `normal`, in-plane axes `u` (width `w`) and `v` (height `h`), `depth`, `shape` (`rrect` | `circle` | `hex` | `grille` | `arc` | `keyhole`), corner `radius`, optional `holes` for speaker grilles, `arc` for grille vents, `keyhole` for wall-plate slots, and for louvres a slanted prism `axis` plus `bevel` / `outerAt` (outer chamfer). All values are final mm in enclosure space.

### Response

```json
{
  "ok": true,
  "objects": [
    { "name": "enclosure_base", "step_b64": "...", "stl_b64": "..." },
    { "name": "enclosure_lid",  "step_b64": "...", "stl_b64": "..." },
    { "name": "standoff_1",     "step_b64": "...", "stl_b64": "..." }
  ],
  "bbox": { "x": 105.82, "y": 75.59, "z": 23.4 },
  "checks": [ { "name": "valid_solid", "pass": true, "detail": "..." } ],
  "log": "...", "error": "only when ok is false"
}
```

Same envelope as the existing `/build` (`ok:false` + plain `error` on any failure, 422 on a malformed request, 500 only for a true internal failure). Units mm, Z up, same origin as the request. Object `name`s: `enclosure_base`, `enclosure_lid`, and each `MechPart.id`, so `BrowserCadBackend` and `CadQueryBackend` are interchangeable in the viewer: load each STL into a `THREE.Mesh` with that name. Rubber feet are children of the base mesh in the browser; the server fuses them into `enclosure_base` (or returns `enclosure_feet`), decided at build time while keeping the viewer stable.

### Mapping: browser step to CadQuery

| Browser (build.ts) | CadQuery |
|---|---|
| Outer solid: rounded-rect (stadium/circle when r reaches the half sides) swept with an edge bevel profile | `cq.Workplane("XY").rect(W, D).extrude(H)`, then `.edges("|Z").fillet(cornerRadius)` and `.faces(">Z").edges().fillet(edgeFillet)`; stadium/circle: `slot2D` / `circle`; soft_wedge: side profile `polyline` extruded; handheld_taper: loft between two rects |
| CSG cavity subtraction (inner outline at inset `wall`, from `floorZ`) | `.faces(">Z").shell(-wall)`, or subtract an inner solid built with the same recipe (needed for tapered shapes) |
| Cut-outs from ports (`plan.cutouts`) | per cut: `cq.Workplane(cq.Plane(origin=center, xDir=u, normal=normal))` then `.rect(w, h)` (or `.sketch().rect(w,h).vertices().fillet(radius)`) and `.cutBlind(-depth)`; `circle` via `.circle(w/2)`, `hex` via `.polygon(6, w)`, `grille` via `.pushPoints(holes).circle(d/2)` |
| Vents (`plan.vents`) | same prism cut, one per slot / hole / hex / grille arc / louvre (patterns `slots`, `holes`, `hex`, `grille`, `louvres`); never within 3 mm of a port, keyhole or the label |
| Lid split at `splitZ`, lip | `intersect` / `cut` with a box at `splitZ`; lid lip ring with gap `LIMITS.lidLip` (0.4 mm), thickness 1.2, height 3, flange 0.9 (`LIP` in templates.ts) unioned onto the lid, minus cut-outs that touch it |
| Feet (`rubber_4`, `ring`) | small cylinders at the corners / a ring under the base |
| Templates | `rounded_box`, `pill`, `soft_wedge`, `puck`, `handheld_taper` as above; all eight are built, no fallback |
| `lantern` | Square rounded body (W = D), H 1.3 / 1.8 / 2.5 × side by heightBias, capped at 3 × (exempt from the 2 × rule); lid = upper band from 0.55 H (`LANTERN_SPLIT`): `rect(W, W).extrude(H)` + the same fillets, split at `splitZ`. Side vents repeat on all four sides of the band (half the count per side) |
| `dome_base` | Circle footprint; cylinder to `dims.dome.z0`, then a half-ellipsoid cap of rise `dims.dome.rise` (0.25 / 0.35 / 0.5 × diameter): `circle(R).extrude(z0)` union a revolved quarter-ellipse (`.ellipseArc` + `revolve`), or `cq.Solid.makeSphere` scaled in z; cavity = cylinder (R − wall) to z0 + the inner ellipsoid (semi-axes R − wall, rise − wall), clipped to (outer − wall) (`innerTopAt`); split 4 mm under the shoulder |
| `wall_plate` | Rounded rect, min side 40, corner radius ≥ 6, height from the parts only (no bias); front = +z top (lid plate); two keyholes through the back (`plan.keyholes`: head 7.5 mm, slot 3.8 × 7 mm towards +y): `.circle(headD/2)` + `.slot2D` cut through the floor; no feet |
| Label (`plan.label`) | Raised 0.6 mm (`LABEL_RAISE`) single-stroke 16-segment text (`label-font.ts`, Latin A–Z 0–9 space - . &), cap 8 → 4 mm, ≥ 3 mm from every opening on its surface; lid top (lantern: the −y face of the band). Each stroke is a capsule (sphere-swept segment) of radius `plan.label.r`, offset along the surface normal so its top is 0.6 mm proud: `cq.Solid.makeCylinder` + two `makeSphere` per stroke (or a sweep of a circle), unioned into the lid. `meta.labelSkipped`: `script` (Arabic), `chars`, `length`, `space` |
| Vent `grille` / `louvres` | grille: arc slots (`cutout.arc`: centre, r, a0, a1, width 1.6, three per ring, bridges 2.4 mm) → `.sketch().arc(...)` offset ± width/2 with round ends, `cutBlind`; louvres: slots on a side face with a slanted axis (`cutout.axis`, 35° outer end down) and a 0.8 mm 45° chamfer at the outer edge (`cutout.bevel`, `outerAt`) → `cutBlind` along `axis` + `.chamfer(0.8)` on the outer edges |
| MechPart (`MECH_BUILDERS`) | one function per template (standoff = cylinder minus hole, pcb_cradle = plate + rails, ...) with `MECH_PARAMS` clamping |

### Validation the server must keep

Re-validate everything (never trust the browser): parse with the same zod schemas, then clamp. Import the TS values as the spec; do not hand-copy numbers.

- `EnclosureSpecSchema` / `LIMITS` (schema.ts): wall 1.6 to 4, clearance 1 to 4, cornerRadius 3 to 20 (and at most 0.33 x the smaller footprint side), edgeFillet 1 to 6 (at most 0.8 x wall), widthToDepth 0.5 to 2.5, ventCount 0 to 24, minFootprint 15, maxHeightRatio 2 (lantern 3), lidLip 0.4, label at most 16 chars. `twist` lid only on `puck`. Louvres only on a side face (else clamped to +x); a `wall_plate` has feet `none`.
- `MECH_PARAMS` per template, [min, max, default]: standoff, pcb_cradle, battery_clip, sensor_mount, cable_clip, button_extender, light_pipe, wall_bracket, lid, base. At most 40 mech parts, ids `^[\w-]{1,40}$`.
- Request size at most 256 KB; cut-outs at most 120; `plan` numbers finite and within the enclosure bbox +/- 5 mm.
- Result must be a valid closed solid with volume > 0 (reuse `app/geometry.py`: `valid_solid`, `positive_volume`, `min_wall`).

### Where it lives

The existing Cloud Run CadQuery worker (`services/cad-worker`, P5-11, Doha `me-central1`) is the natural home: add `POST /studio/build` next to `POST /build`. It reuses the child-process runner, the 45 s timeout and the geometry checks; no AI code runs (JSON only), so `sandbox.py` is not needed. Auth is unchanged: Vercel OIDC to Google STS (Workload Identity Federation) to an ID token for the service URL (`lib/cad/cloud.ts`, keyless). A server-only `lib/studio/cad-cloud.ts` would mirror `cloud.ts`, called from a route such as `app/api/studio/cad/route.ts`.

Limits to set before enabling:

- Timeouts: worker 45 s per build (`CAD_BUILD_TIMEOUT_S`), Vercel route 60 s, queue wait 50 s then a plain "busy".
- Concurrency 1 per instance (`CAD_MAX_CONCURRENT_BUILDS`), max instances capped (start with 2), scale to zero.
- Cost: a build is a few CPU-seconds on 2 vCPU / 2 GiB. Keep the owner's USD 1 / 5 / 10 budget alerts; add a per-user daily cap (suggest 20 builds) and a global daily cap, checked server-side before the call. The browser path stays the fallback on any error: a down worker must never block the Studio.

### Rollout

1. Implement `/studio/build` and tests in `services/cad-worker` (JSON tests need no CadQuery; geometry tests run in the Cloud Build image like P5-11).
2. Implement `CadQueryBackend`; extend `parseStudioCadSetting` to accept `"cadquery"` and `"admin"` (cloud for super_admin only, like `resolveCadEngine`). Until then the parser deliberately rejects them.
3. Admin-only: the owner compares browser vs CadQuery output on the same products (volume, bbox, cut-out positions).
4. Then `cadquery` for everyone if cost and failure rate are fine. Switching back to `browser` is instant (cached for the storefront revalidate window).

### The switch (SQL, not run, no migration)

The row is optional; with no row the Studio uses the browser. To create it explicitly:

```sql
insert into public.store_settings (key, value)
values ('studio_cad', '{"backend": "browser"}'::jsonb)
on conflict (key) do nothing;
```

Later, once the backend exists (do not run before):

```sql
update public.store_settings set value = '{"backend": "cadquery"}'::jsonb where key = 'studio_cad';
-- back to normal at any time:
update public.store_settings set value = '{"backend": "browser"}'::jsonb where key = 'studio_cad';
```
